Treat all host/VPS specifics below as **unknown**; obtain owner confirmation.

## 5. Coordinated stop-writers release sequence (approval request, not execution)

Rolling deployment is **not** assumed safe. Sequence, with every step gated on owner approval:

1. **Preflight** — record base/head SHAs and CI; confirm the exact Compose project, database and host; confirm current migration history, table counts and data-shape snapshot with a read-only query; confirm auth/TLS/host allow-list/secret/debug settings are in place (repo does not evidence them); confirm the new images are pinned and staged locally; stage both old and new artifacts (`ops/deployment/release.py build/archive/prepare`), never build on the production database.
2. **Protected backup** — stop application writers first, then dump the quiesced DB with `pg_dump`/`pg_restore`-verified custom format; record SHA-256 in protected storage outside Git and volumes; verify restoration on a disposable database (`ops/deployment/rehearse.py`, `release.verify_backup`, `ops/deployment/integrity.py`); **never identify the backup by filename alone** (0033 incident).
3. **Stop writers** — remove public ingress; pause `refresh_availability`, `refresh_provider_catalogue`, both queue workers, all cron/timers and manual jobs; drain in-flight work; stop **every** replica of `backend`, `worker`, `catalogue-worker`; check for standalone processes, one-off Compose runs and other clients of the same DB; verify quiescence. Gate B of `release.py` explicitly requires an exclusive-maintenance token `<gate>:<project>:<database>@<host>` plus `--quiescent <project>:<database>@<host>`.
4. **Migration** — review `migrate --plan` with the staged image; apply only through the confirmed `migrate` service with exact `EXPECTED_DATABASE_NAME`, `EXPECTED_DATABASE_HOST`, `CONFIRM_MIGRATION_TARGET`; for combined releases apply availability 0018 before 0020 and tracker 0064 in the reviewed order; verify `showmigrations` and `migrate --check` against the release image **before** starting runtime services.
5. **Deploy application** — recreate backend from the staged image with ingress still paused (`docker compose up -d --build --force-recreate backend`); verify the entrypoint is `/bin/sh /runtime-guard-entrypoint.sh` mounted read-only and that the guard mount is present (`docker inspect`); keep workers stopped until checks pass.
6. **Verify read/write compatibility** — `migrate --check` exit 0; cached read-only checks of existing price/provenance that cannot enqueue or call a provider; old-shaped insert smoke test on a **disposable** database with mocked transport; confirm entitlement tables are empty and all verdicts are `UNKNOWN` (Activation A) before any mapping is enabled.
7. **Health checks** — `curl -I /api/health/` → 200 `{"status":"ok","db":"ok"}`; `curl -I /api/providers/` → 200 (verified disposable via Django test client); container healthcheck `ops/deployment/health.py`; inspect backend/worker/catalogue logs for insert failures and guard errors.
8. **Rollback decision** — explicit owner decision point; see §9.
9. **Resume writers** — only after steps 6–8 pass, restart approved writers one lane at a time, watch logs, then restore cron/schedules. `release.py` Gate E is **review-only**: all schedules remain disabled; no worker activation is implemented and separate provider-specific approval is required.
10. **Post-deployment monitoring** — watch health, error rates, migration state, entitlement `UNKNOWN` rates, worker backlog, API budget and scheduler readiness for at least one refresh cycle; keep the protected backup until the window closes.

## 6. Backup and recovery procedures — exact descriptions

- **Documented manual backup** (`docs/DEPLOYMENT.md:231-271`): `mkdir -p ./backups`; `docker compose exec db pg_dump -U tracker tracker > ./backups/tracker_backup_$(date +%Y%m%d_%H%M%S).sql`; optional `gzip ./backups/*.sql`; secure `./backups` with `chmod 700`. Restore: `docker compose stop backend frontend worker`; gunzip if needed; `docker compose exec -T db psql -U tracker -d tracker < ./backups/tracker_backup_YYYYMMDD_HHMMSS.sql`; `docker compose start backend frontend worker`. Warning: test restorations in staging first; dumps contain sensitive data.
- **Hardened release backup** (`ops/deployment/release.py` / `rehearse.py`): Gate B verifies the unchanged baseline (48 tables on the 0056 line), stops backend, takes `before-migrations.dump` into the bundle with a recorded SHA-256, verifies it through `verify_backup`, then runs `check_plan.py` to reject any migration outside the reviewed incremental plan.
- **Restore recovery** (`ops/deployment/recover_database.py`): requires exact approval token `restore:<project>:<database>@<host>:accept-post-backup-data-loss` plus `--quiescent <project>:<database>@<host>`; re-verifies the dump checksum and backup; creates a new `<database>_restore_<ns>` database, `pg_restore --no-owner --no-acl --exit-on-error` into it, verifies tables/migration history against `baseline.json` and runs `migrate --check`; terminates connections, renames the original to `<database>_failed_<ns>` (**retains it, never drops it**), promotes the restored database, deploys the old image, and supports `--resume` from durable progress stages `RESTORE_VERIFIED` / `ORIGINAL_RENAMED` / `RESTORED_PROMOTED`. Explicitly accepts post-backup data loss.
- **Application rollback** (`release.py` gate `rollback`) retains the expanded schema and all evidence, redeploys the old image and asserts the integrity snapshot is unchanged; it does not revert migrations.
- Gap: the manual SQL dump is plain text and the doc uses host ports 8000/3001 while the Compose default backend port is 8002; reconcile against the actual deployment before relying on those commands.

## 9. Rollback and abort conditions

- **Abort before migration** if: target DB/host/confirmation token mismatch; backup checksum or restore verification fails; any writer is still connected; migration plan contains an unexpected migration;guard mount missing; production shape differs from the reviewed snapshot without an updated plan; any live-provider call is required.
- **Abort during/after migration** if: `migrate --check` fails on the release image; guard or health checks fail; new insert paths fail; entitlement verdicts turn positive without reviewed evidence; unexpected schema/table drift.
- **Rollback options:** (a) application-only rollback to the pinned old image, retaining the additive 0064 schema and all evidence (fastest; verified pattern in `release.py` gate `rollback`); (b) full restore from the verified protected backup via `recover_database.py`, with explicit acceptance of post-backup data loss, original database retained as `_failed_`; (c) schema downgrade `tracker 0064 → 0063` is reversible in isolation (verified here) but only under a separately reviewed plan if the DB carries later migrations. For availability 0018, downgrade deletes all stored variants — recover them from a compatible backup/export or accept the loss.
