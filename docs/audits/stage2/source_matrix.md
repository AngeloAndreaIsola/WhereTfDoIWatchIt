## Shared source policy and persistence behavior

- Exact registrations: `availability/sources/__init__.py:38-54`; capabilities in each adapter's `capabilities` declaration.
- Role map is exhaustive and tested (`tracker/services/source_policy.py::SOURCE_ROLES`): 11 collectors, JustWatch/Watchmode broad aggregators, Streaming Availability metered aggregator.
- Source is the information origin; Provider is where a user watches. Provider mapping goes market-specific → global mapping → JustWatch static mapping → enabled provider slug (`availability/services/refresh.py:1049-1098`). Unknown IDs are skipped, not turned into providers or subscriptions.
- All registered adapters in the capability audit declare non-authoritative snapshots. Absence from an aggregator, incomplete page walk, timeout, schema error or budget exhaustion must not deactivate another source's positive offer.
- Per-source freshness windows are in `availability/freshness.py:66-96`. The live config override currently affects read classification but not scheduling (A6).
- Direct catalogue sync is separate from title-targeted refresh. `supports_title_fetch` and `supports_catalogue_sync` are independent capabilities; title-level source list is capability-derived.
- Retry/backoff and request count are client-specific. Watchmode counts each outbound retry attempt; coordinator reservation double-charge is fixed in this audit branch (A2). Streaming Availability counts at its HTTP call seam and avoids duplicate coordinator reservation.

## Activation status

The read-only local PostgreSQL snapshot contained two `Source` rows, both enabled: JustWatch and Watchmode. The other 12 registrations have no corresponding row in that database. This snapshot is not proof about a deployed environment. Credentials, endpoint reachability and current upstream quotas were not inspected or exercised. Do not describe all 14 as active collectors based only on registration.
